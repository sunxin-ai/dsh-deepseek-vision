# eval —— 这只借来的眼睛，够不够格当裁判

## 这套评测为什么存在

**最终目标是在 DSH 上做出「产品设计」这项插件能力** —— 从设计稿出发写出实现，
再自己判断实现得像不像，不像就修，修完再判，直到收敛。这个闭环里最关键的一环是**判定**：
没有可信的判定，循环要么永不停止，要么在错误的地方停下。

卡点在于 **DeepSeek 是纯文本模型**：它写得了代码，却既看不见设计稿，也看不见自己写出来的
页面长什么样。判定这一环它做不了。

`dsh-design-qa` 的做法是**通过一个工具把多模态能力借给它** —— 图片不进它的上下文，
它需要看的时候调 `deepseek_vision`，由一个真正的视觉模型代看，把文字带回来。
于是 DeepSeek 具备了执行产品设计功能所需的那只眼睛。

**这套评测回答的就是最后那个问题：借来的这只眼，够不够格当判定闭环里的裁判。**

「能看见」和「可用于判定」是两回事。一个模型可能读得出图上的字，却：

- **看得见但不主动看** —— 开放式提问下漏掉难档缺陷（实测确有此事，见下）
- **看得见但会编** —— 把设计稿和它自己配对，仍报出「差异」
- **看得见但不稳** —— 同一张图三次判定三个结论，循环因此震荡不收敛
- **看得见但说不清** —— 「颜色不一致」这种结论无法据此改代码

四条通过线一一对应这四种失效方式。**全过才算这只眼可以进生产判定循环。**

---

**换供应商或换模型后，跑一遍这个再上生产。** 默认的 `qwen3.8-max` 是这么选出来的，
换成别的模型时，凭直觉判断「这个模型应该也行」是不够的。

## 目录

| | |
|---|---|
| `RUBRIC.md` | 基准规范：夹具怎么造、缺陷怎么分档、四条通过线、混杂因素与排除方法 |
| `evalset/` | 4 组夹具（landing / dashboard / list / form），**23 处缺陷**，难 9 / 中 8 / 易 6 |
| `tilebench.py` | 跑判定，支持多供应商（OpenAI 兼容端点） |
| `score_facets.py` | 打分，只统计表态分布，**不做关键词自动判分** |
| `pair.mjs` | 把设计稿与实现的区块图并排拼成送检图 |
| `runs/` | **本文与 `../README.md` 里每个数字的原始模型输出**，逐格未编辑，含各自用的夹具 |

每组夹具是 `design.html`（设计稿）+ `v1.html`（忠实实现）+ `v2.html`（注入版）+ `defects.md`（真值）。
`v1` 与 `design` 的残余差异 0.018%–0.185%，全部落在自绘图标笔画与文字亚像素上。

**当前跑分覆盖的是 `landing` 一组。** 真值四组齐全（23 条，`evalset/fixtures.mjs` 有机器可读版，
`assert.mjs` 做像素级注入断言），但 `tilebench.py` 的 `REGION_NAMES` 只定义了 `landing` 的 6 个
区块描述，`facets` / `pairs` 跑另外三组会在查不到区块名时抛 `KeyError`。

要覆盖全部 23 条得改两处：`tilebench.py` 的 `REGION_NAMES` 补齐另外三组的区块描述（跑得动），
`score_facets.py` 改成读 `evalset/fixtures.mjs` 而非硬编码的 `LANDING_DEFECTS`（算得出召回）。
`facets` / `pairs` 这两条命令本身不硬编码夹具 —— 它们按 `pairs/{fixture}__{arm}__{region}.png`
的文件名遍历，所以补齐区块名之后不需要再动它们。

`REGION_NAMES` 里另有 `header` / `ring` / `stats` / `chart` / `tabbar` 五个区块，**不属于 `evalset/`**：
它们是 `probe` / `judge` 两条命令的区块常量 `REGIONS`，服务于 `runs/probe-mobile/` 那组夹具。
补齐时要留着它们；`header` 与 `chart` 在 `evalset/` 里同名而不同物，需要按夹具区分，
否则会静默送出一段描述错对象的提示词。

## 跑之前

`evalset/shoot.mjs` 与 `assert.mjs` 需要 Playwright，本包**不把它列为依赖**（插件运行时用不到）：

```sh
cd eval && npm i && npx playwright install chromium
export PLAYWRIGHT_BROWSERS_PATH="$PWD/.playwright"   # 别装到 ~/Library，DSH 沙箱拒绝
node evalset/shoot.mjs --crops                       # 出截图与区块裁剪
node pair.mjs --left <design裁剪> --right <impl裁剪> --out pairs/<名字>.png
```

`tilebench.py` 读的 `pairs/` / `tiles/` / `composite/` 都由上面两步生成，**不随包分发**
（都是可再生的中间产物，且体积大）。

## 四条通过线

1. **难档缺陷至少命中 1 项** —— 证明有语义级判断力，而非 OCR + 取色器
2. **零差异对照幻觉 ≤ 1 条** —— 把设计稿和它自己配对，报出的任何差异都是幻觉
3. **命中项 A 级可执行性 ≥ 50%** —— 「颜色不一致」无法据此改代码
4. **同图三次独立判定，共同项 ≥ 60%** —— 不稳定则循环震荡

四条全过才算「可用于生产判定」，只过 1、2 算「可用于人工辅助评审」。

## 三条会让你白测的陷阱

都写在 `RUBRIC.md` 里，照做即可：

**一、夹具会静默损坏。** 拼图脚本若用 `page.setContent()` 加载 `file://` 图片，
子资源会被静默拦截（`setContent` 的文档源是 `about:blank`），而
`waitForLoadState('networkidle')` 照样返回成功 —— 整轮基准跑在两块空白图上，
模型如实回答「图像未加载」，很容易被记成「模型编造分析」。
→ **拼图一律走 data URI 并断言 `naturalWidth > 0`；评测集常驻一张已知空白图作对照。**

**二、二选一的方向题，单次命中是运气。** 「左边更粗」答对一次说明不了什么：
扩到 15 次只对 8 次 —— **53% 就是掷硬币**。错误还按**轮次**聚集，单看任何一轮都像稳定的。
→ **方向类判定必须跑满 3 次才计分。**

**三、字重 600/700/800/900 在常用字体栈下渲染成同一字面。** 注入 800→600 在像素上完全无效。
→ **字重类缺陷用 800→500 / 700→500，且注入后必须做像素级断言。**

## 提问方式比模型选型更决定成败

同一个模型、同一批图，**换的只是问法**：

| 提问形式 | 零差异对照的幻觉 | 难档召回 |
|---|---|---|
| 「你自己找差异」 | 0/30 | 0/2 |
| 「这个方面有区别吗」 | 0/30 | 0/2 —— 判定题，模型默认答否 |
| 「哪个更大」 | 0/36 | 1/2 —— 留白类被系统性答反 3/3 |
| **「各自是多少」** | **0/12** | **2/2** |

注意第一行的低幻觉率**有一部分是「懒」换来的** —— 大量回答「一致」，说得少自然错得少。
所以召回和幻觉必须一起看，单看任一项都会得出错误结论。

### 这张表能复核到什么程度

**四种问法里，评测脚本只实现了一种。** `tilebench.py` 的 `FACETS` 五个保真面统统以
「有区别吗」结尾，对应第二行：

| 行 | 脚本里的对应 | 原始输出 |
|---|---|---|
| 「你自己找差异」 | `cmd_pairs` 的 `REGION_PROMPT` 是开放式，大致对得上 | 有，但没单独计过分 |
| **「这个方面有区别吗」** | **`cmd_facets` + `FACETS`** | **有，`runs/facets-landing/`** |
| 「哪个更大」 | 无 | 无 |
| 「各自是多少」 | 无 | 无 |

后两行**没有提示词常量、没有命令、没有输出文件**，`0/36` 与 `0/12` 这两个网格也对不上脚本里
任何一种格数（`facets` 是 6 区块 × 5 保真面 = 30，`pairs` 是每 arm 6 格）。

**可复核的那一行里还有一处要打折扣。** `runs/facets-landing/_facets-bailian.txt` 逐格核下来：

- `design` arm 30 格全报「一致」，**0 条幻觉 —— 0/30 属实**
- `v2` arm 的两处难档，一处是真漏（`hero-head / 字体排印` 报「一致」，而 L1 是字重 800→500），
  另一处**请求根本没回来**（`seam-features-cta / 间距节奏` 是 `__RemoteDisconnected__`）。
  另有一格 `hero-head / 素材保真` 是 `__URLError__` SSL 中断。

也就是说难档那个 `0/2` 是「一处真漏 + 一处从未拿到回答」，不是两次都测出来了。

**结论方向不受影响** —— 判定题式提问在难档上确实没抓到东西，这在原始输出里看得见。
受影响的是精度：这张表记录的是真实做过的事，但只有第二行的幻觉数经得起逐格复核。

这套纪律固化在 `../skills/design-qa/SKILL.md` 里，不写死在工具中 ——
提问由模型按 skill 组织，实测比写死的模板更准。

## 读数的可信边界

**方向可信，量级不可信。** 实测字重真值 800/500 读作 800/700，间距 80/25 读作 72/38 ——
被测侧总被拉向参照侧。

用它判断「有没有差异、往哪个方向」，**不要当测量值**；实现侧的精确值用
`getComputedStyle` 或像素测量取得。视觉模型不可替代的地方只有一处：
**设计稿那一侧只有像素，没有 DOM。**
