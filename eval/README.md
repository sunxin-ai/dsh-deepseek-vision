# eval —— 换模型后用它重测

**换供应商或换模型后，跑一遍这个再上生产。** 「能看见」和「可用」是两回事：
一个召回高但幻觉多、或每次结论都漂移的模型，会让判定循环发散而不自停。

## 目录

| | |
|---|---|
| `RUBRIC.md` | 基准规范：夹具怎么造、缺陷怎么分档、四条通过线、混杂因素与排除方法 |
| `evalset/` | 4 组夹具（landing / dashboard / list / form），**23 处缺陷**，难 9 / 中 8 / 易 6 |
| `tilebench.py` | 跑判定，支持多供应商（OpenAI 兼容端点） |
| `score_facets.py` | 打分，只统计表态分布，**不做关键词自动判分** |
| `pair.mjs` | 把设计稿与实现的区块图并排拼成送检图 |

每组夹具是 `design.html`（设计稿）+ `v1.html`（忠实实现）+ `v2.html`（注入版）+ `defects.md`（真值）。
`v1` 与 `design` 的残余差异 0.018%–0.185%，全部落在自绘图标笔画与文字亚像素上。

## 跑之前

`evalset/shoot.mjs` 与 `assert.mjs` 需要 Playwright，本包**不把它列为依赖**（插件运行时用不到）：

```sh
cd eval && npm i && npx playwright install chromium
export PLAYWRIGHT_BROWSERS_PATH="$PWD/.playwright"   # 别装到 ~/Library，DSH 沙箱拒绝
node evalset/shoot.mjs --crops                       # 出截图与区块裁剪
node pair.mjs --left <design裁剪> --right <impl裁剪> --out pairs/<名字>.png
```

`tilebench.py` 读的 `pairs/` / `tiles/` / `composite/` 都由上面两步生成，**不随包分发**
（都是可再生的中间产物，且体积大）。

## 四条通过线

1. **难档缺陷至少命中 1 项** —— 证明有语义级判断力，而非 OCR + 取色器
2. **零差异对照幻觉 ≤ 1 条** —— 把设计稿和它自己配对，报出的任何差异都是幻觉
3. **命中项 A 级可执行性 ≥ 50%** —— 「颜色不一致」无法据此改代码
4. **同图三次独立判定，共同项 ≥ 60%** —— 不稳定则循环震荡

四条全过才算「可用于生产判定」，只过 1、2 算「可用于人工辅助评审」。

## 三条会让你白测的陷阱

都写在 `RUBRIC.md` 里，照做即可：

**一、夹具会静默损坏。** 拼图脚本若用 `page.setContent()` 加载 `file://` 图片，
子资源会被静默拦截（`setContent` 的文档源是 `about:blank`），而
`waitForLoadState('networkidle')` 照样返回成功 —— 整轮基准跑在两块空白图上，
模型如实回答「图像未加载」，很容易被记成「模型编造分析」。
→ **拼图一律走 data URI 并断言 `naturalWidth > 0`；评测集常驻一张已知空白图作对照。**

**二、二选一的方向题，单次命中是运气。** 「左边更粗」答对一次说明不了什么：
扩到 15 次只对 8 次 —— **53% 就是掷硬币**。错误还按**轮次**聚集，单看任何一轮都像稳定的。
→ **方向类判定必须跑满 3 次才计分。**

**三、字重 600/700/800/900 在常用字体栈下渲染成同一字面。** 注入 800→600 在像素上完全无效。
→ **字重类缺陷用 800→500 / 700→500，且注入后必须做像素级断言。**

## 提问方式比模型选型更决定成败

同一个模型、同一批图，**换的只是问法**：

| 提问形式 | 零差异对照的幻觉 | 难档召回 |
|---|---|---|
| 「你自己找差异」 | 0/30 | 0/2 |
| 「这个方面有区别吗」 | 0/30 | 0/2 —— 判定题，模型默认答否 |
| 「哪个更大」 | 0/36 | 1/2 —— 留白类被系统性答反 3/3 |
| **「各自是多少」** | **0/12** | **2/2** |

注意第一行的低幻觉率**有一部分是「懒」换来的** —— 大量回答「一致」，说得少自然错得少。
所以召回和幻觉必须一起看，单看任一项都会得出错误结论。

这套纪律固化在 `../skills/design-qa/SKILL.md` 里，不写死在工具中 ——
提问由模型按 skill 组织，实测比写死的模板更准。

## 读数的可信边界

**方向可信，量级不可信。** 实测字重真值 800/500 读作 800/700，间距 80/25 读作 72/38 ——
被测侧总被拉向参照侧。

用它判断「有没有差异、往哪个方向」，**不要当测量值**；实现侧的精确值用
`getComputedStyle` 或像素测量取得。视觉模型不可替代的地方只有一处：
**设计稿那一侧只有像素，没有 DOM。**
